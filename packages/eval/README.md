# Does the adaptive loop actually work?

The test suite proves the code does what it was built to do. It proves nothing about whether the
**mechanism** — dispute, tightened threshold, fewer repeat bad purchases — holds up across a
household's history. That is a different question, and it needs evidence.

```bash
npm run eval
```

Every number below is regenerated by that command and committed to `results/`.
`test/claims.test.ts` reads those files back and fails if anything here has drifted from them.

## What is being measured, and what is not

**This is not a claim about real households.** Nobody has run Vouch in a real home. The behaviour
here is synthetic.

What it *is* is a falsifiable experiment on the mechanism. Given an agent whose confidence is only
loosely correlated with what a household actually wanted — the only interesting case, since a
perfect agent needs no gate — does moving the threshold from disputes beat leaving it alone?

200 households × 60 purchase opportunities = **12,000 decisions**, seed `20260923`. Both arms see
*identical* histories; the only difference is whether a dispute may move the threshold. The two
confidence distributions overlap heavily (wanted: mean 0.88, unwanted: mean 0.80, wide spread), so
no threshold cleanly separates them. A well-separated agent would flatter the loop and would also
mean the gate was barely needed.

**How it could fail.** Tightening has a price: the move that blocks an unwanted purchase also
blocks a wanted one near the boundary. If harm falls only as fast as usefulness, the loop is an
expensive way of doing nothing. Both are measured and both are reported.

## The result, at the tuning that ships

Final quarter of each history, where a loop that learns should show up:

| | adaptive | static |
|---|---|---|
| unwanted purchases completed | **185** | 272 |
| reduction | **32.0%** | — |

And what it cost, across the whole run:

| | adaptive | static |
|---|---|---|
| unwanted purchases completed | 826 | 1,096 |
| wanted purchases held | 4,100 | 2,980 |
| wanted purchases completed | 4,350 | 5,470 |
| mean final threshold | 0.886 | 0.850 |

**A third fewer unwanted purchases, for 1,120 wanted ones held for approval.** Whether that is a
good trade depends on how much a wrong purchase costs a household relative to being asked. It is
not obviously good, and the README should not pretend otherwise.

## Why the default is not tuned harder

It was. At +0.07 per dispute the same trial cuts late-history harm by **76.8%** — and leaves the
agent completing **31.3%** of what the household actually wanted, with the mean threshold ratcheted
to 0.957.

**That is not a good product.** An agent that careful is not trustworthy, it is switched off. The
default was changed to +0.03 on this evidence.

## The trade-off curve

There is no setting that gets both. The frontier is published so the operating point can be
argued with rather than taken on trust:

| tuning | harm cut | extra held | agent still useful | final threshold |
|---|---|---|---|---|
| none (control) | 0.0% | 0 | 64.7% | 0.850 |
| +0.01 / recover 2 | 6.6% | 208 | 62.3% | 0.854 |
| +0.02 / recover 2 | 17.6% | 573 | 58.0% | 0.864 |
| **+0.03 / recover 2 (shipped)** | **32.0%** | **1,120** | **51.5%** | **0.886** |
| +0.03 / recover 3 | 45.2% | 1,439 | 47.7% | 0.903 |
| +0.07 / recover 3 | 76.8% | 2,823 | 31.3% | 0.957 |

**The default was changed from +0.07 to +0.03 on this evidence.** 0.07 was picked by intuition.
A household that has been burned may well want it back, and the constructor takes it.

## Two things this found that tests had not

**1. Recovery had no floor.** With few disputes, a run of undisputed purchases dragged the mean
threshold from the 0.85 a household chose down to **0.669**, and unwanted completions rose **178%**
against a static mandate. The agent was quietly granting itself more latitude than anyone had
given it — through the mechanism meant to reward good behaviour.

That breaks this project's own rule that *the agent may do anything that cannot increase its own
authority*. `Mandate.baseline_confidence_threshold` now floors recovery: a dispute tightens away
from the household's number, a good streak returns toward it, and nothing but the household moves
the number itself.

The control row above reads 0.0% / 0 cost only **after** that fix. Before it, the control was
actively harmful, which is how the bug surfaced.

**2. The shipped tuning throttled the agent.** Covered above.

Both were invisible to 131 passing unit tests, because each component did exactly what it was
written to do. The failure was in the composition, over time.

## Restocking from a forecast, versus a calendar

Amazon's Scheduled Actions restock on a calendar. The household model (`packages/household`)
restocks from a forecast of when *this* house runs out. Does that actually do better?

**Synthetic, like everything in this file.** 200 households × 6 items × 365 days = **1,200
item-years**, seed `20260927`. Each household's real pace sits around the category guess (log sd
0.35); each pack varies (log sd 0.2); guests occasionally visit and use 1.6× as much; households say
"we're out" only **70%** of the time, answer "how much is left?" 80% of the time, roughly.

**The baseline is unflattering on purpose:** a calendar set to the household's **own stated
interval** — the best a calendar could do — not a generic "every month" (reported too).

| policy | days out of stock | stock in the house | packs bought | deliveries too early | asks per household per week |
|---|---|---|---|---|---|
| **forecast, asks once per pack (default)** | 3,375 | 18.3 days | 24,654 | 843 | 2.6 |
| forecast, never asks | 1,301 | 64.3 days | 31,065 | 20,665 | 0 |
| forecast, asks weekly | 2,025 | 17.9 days | 24,766 | 945 | 4.1 |
| calendar, household's own interval | 4,295 | 40.0 days | 27,456 | 12,133 | 0 |
| calendar, monthly | 16,812 | 32.0 days | 24,404 | 3,471 | 0 |

**Against the fair calendar, the default forecast runs out 21.4% less, keeps 54.2% less stock in
the house, buys 10.2% fewer packs, and delivers too early 93.1% less often.**

**What it cost: 2.6 one-tap questions per household per week** across six items ("roughly how much
is left — almost out, half, a full one?"). That is why it is a household setting, not hidden:
asking weekly runs out 52.9% less at 4.1 questions a week.

**Never asking is not free either.** It runs out least (69.7% less) — by hoarding: 60.8% more stock
in the house and 13.1% more packs bought. An agent that never checks can only avoid running out by
buying early.

**The forecast is calibrated, not just better.** Its "days left" is off by 7.3 days on average,
and the real value fell inside its stated 80% range 79.7% of the time — it is as unsure as it says.

### What this found that the unit tests had not

The first version averaged **90 days** of stock in the house. An agent that buys *before* the house
runs out never hears "we're out", so it never learned, and projecting ten bottles ahead from the
first turned a 25% pace error into months. The "how much is left?" answer — re-anchoring the stock
and teaching the pace — exists because of that run. So does the rule that silence is never treated
as "still lasting".

## Honest limits

- Synthetic households, not real ones.
- One confidence model. A different overlap between wanted and unwanted would move every number.
- Disputes are assumed perfect: every unwanted purchase is complained about, immediately. Real
  households are inconsistent, and that would weaken the signal the loop learns from.
- One seed. The figures are reproducible, not distributionally characterised.
- Restocking: consumption, reporting and answer accuracy are all assumed, not measured. Delivery is
  a fixed 2 days. A household's pace is assumed stable apart from guests; a new baby or a new dog
  would need a real change detector, which the model does not have.
